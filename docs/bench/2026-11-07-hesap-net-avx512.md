## Machine and arms

Spot c4-standard-8, Intel Xeon Platinum 8581C, 8 vCPUs, Ubuntu 24.04, GCC 13.3.0, the `linux-gcc-release` tree with the boards'
peers on. `cpu detected=avx512 selected=avx512`, GFNI present. One machine for one run: 21 minutes, about 0.06 USD, created with
`bench_vm.py create --once 3` and deleted with its disk. Boards ran as on the i9-14900K, one thread. These are one run's figures
from the board's output: the machine was deleted before its raw files were copied. Only the ratios inside a run compare with other
boards, never the absolute numbers.

## Quantisation, nanoseconds per value (`--rounds 25`)

| Family | Peer, encode / decode | avx2 | avx512 | avx512 over the peer |
|---|---|---|---|---|
| bounded float, 18 bits | 5.06 / 2.66 | 0.24 / 0.20 | 0.23 / 0.21 | 21.8x / 12.8x |
| smallest three, 9 bits | 22.89 / 12.06 | 2.64 / 7.72 | 2.02 / 4.72 | 11.3x / 2.6x |
| smallest three, 15 bits | 22.89 / 11.91 | 2.63 / 7.71 | 2.02 / 4.72 | 11.3x / 2.5x |

Before this run's fix the bounded float's encode was 0.61 on avx512 and 0.37 on avx2, its decode 0.25 and 0.23; smallest three's
encode 2.66 and 3.22. Each `select` on AVX-512 turned a mask into a vector and back (`vpmovm2d`, `vpmovd2m`; GCC keeps both), and a
store through the codes could alias the format's `max_code`, so it was reconverted per block. `min` and `max` give the same bytes.
With serialize's stream paid on hesap's side too, avx512 is 5.3x on encode and 2.5x on decode.

**Open: the planned rows at K = 10 and 101.** Two findings bound it. Holding hesap's symbols on 64-byte lines moved no row beyond
run noise, so it is not line splits. Plain AVX2 tables (`CRD_CPU_LEVEL=avx2`) beat AVX-512 with GFNI on hesap's planned K = 1000
(13,615 against 12,227, interleaved) and lose at K = 10 (7,594 against 10,836). The board's profile had too few samples to name the
hot phase at K = 10, so the cause is not isolated.
