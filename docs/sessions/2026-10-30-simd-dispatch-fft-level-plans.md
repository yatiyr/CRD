## User decision recorded

Asked in batches 112 to 116 whether fft keeps one plan on every level (cross-level bits) or takes each level's
fastest plan. The user chose **"C": both plans, chosen explicitly.** By default each CPU level runs its fastest
measured plan per size; across levels fft is then held to a declared tolerance against the portable reference. A
determinism mode keeps the one canonical plan on every level, so its bits are identical across levels (replays,
lockstep, golden tests); it reuses the engine's determinism-mode concept in its owning module. Tests: bit-exact within
each level in both modes, across levels in determinism mode, within the tolerance across levels by default, and the
mode changes a plan only where the board shows a per-level winner. The plan table is data derived from the saved
board; one confirmation run, no sweeps.

## Where the mode lives

ADR-0052 §7 "Determinism mode" is the world's fixed step (`step_fixed`), not a runtime switch. The engine's runtime
modes were eylem's `DeterminismMode` (Default: same-machine replay; CrossPlatform: bit-exact across compilers,
architectures and levels; BackwardCompat reserved), which already state C's two meanings. ADR-0063 places the
determinism substrate in crd-math, so the enum moved to `crd/math/determinism_mode.hpp` and eylem aliases it
(values pinned, `is_same` checked). The process's kernel mode is `crd::math::kernel_determinism()` and
`set_kernel_determinism()` beside the dispatch tables (`kernel_dispatch.hpp`, an atomic in crd-math), set by code,
read when a plan is built. Board records and the doctor need no field: no environment variable sets it, so every
board and diagnostic process runs Default.

## The plans

- `fft::detail::level_forward<T>(n, level, mode)`: under Default the board's row of the type, level and size, the
  canonical `planned_forward` otherwise and where the board has no row. `FftPlan(alloc, n)` reads the process's kernel
  level and mode once; four-step sub-plans stay canonical (the composition the board measured). The inverse is
  unchanged.
- `level_plans_gen.hpp` is generated by `scripts/gen_fft_level_plans.py` from the board's data file (every arm's time
  per pass, `docs/bench/2026-10-30-simd-dispatch-fft-f32-arms.json`; `--import` reads a board directory): the fastest
  median where every pass beat every pass of the level's planned arm (equal medians: the lower mean), the planned arm
  otherwise. It is in `generated-sources.json` with its `--check`.
- Board 2's arms gave the first table. One confirmation pass agreed at avx2, sse4.2 and sse2 at every size; at
  portable Stockham led at six sizes, because `f70b933d` (inlined f32 fma) changed portable after board 2. Board 3
  re-ran the five passes on the current engine (5.4 minutes) and the table comes from it: portable, sse2 and sse4.2
  run their own plans at 1K to 1M, 1.08x to 1.96x faster than the canonical plan in the same run; 2M, 4M and every
  avx2 size stay canonical.
- Declared tolerance: each plan meets the ADR-0092 §5 class against the radix-2 reference (max |a - b| / (1 + max |b|):
  f64 1e-12, f32 2e-4 and 1e-3 from 512K), so two levels' default plans differ by at most twice it. The board's
  measured errors against an FFTW f64 truth are 1.0e-7 to 3.8e-7 on every arm.
- Not measured, so canonical: f64, every inverse, avx512 and neon. Board 2 shows f64 at sse2 and sse4.2 1.6x to 1.9x
  behind portable at every size it lists; that is the fft item the row now names.
