## The workload

`io` in `tests/support/diag-overhead/workloads.cpp`, no new file. Setup writes eight 256 KiB files of generated bytes
into `--scratch` (every mode; teardown removes them) and opens each as an `AsyncFile`. A frame submits 32 16 KiB
`AsyncFile` reads to the crd-jobs pool, reads two files whole (`read_file_binary`) and 16 chunks (`read_file_range`)
on the main thread meanwhile, then waits for every completion: the three reads the I/O fault seam consults, 1.25 MiB
and 50 reads a frame, one informational site each. Every read is hashed (FNV-1a over 8-byte words), and the expected
signature comes from the byte generator, so a wrong, short or failed read fails the frame. The pool start and stop
the `jobs` workload had moved to a shared `PooledWorkload` (the host's watchdog window, the jobs adapter in full).
The harness links `crd-platform`; `diag-overhead.py` and `sample-overhead-wpr.py` (6,000 frames, about 3.6 s) list
the workload, and three CTests join the twelve.

The pool is two threads whatever `--threads` says. On the Linux reference host (WSL2) frames grow with completion
workers, in every arm alike, the compiled-out one included; Windows is flat:

| Pool threads (affinity 5555) | Linux p50 / p95, frames above 1.4 x p50 | Windows p50 / p95 |
| --- | --- | --- |
| 2 | 203 / 231 µs, 3 of 300 | 621 / 682 µs |
| 3 | 208 / 256 µs, 6 of 300 | 594 / 639 µs |
| 4 | 230 / 422 µs, 104 of 300 | 593 / 635 µs |
| 8 | 399 / 450 µs, 1 of 300 | 590 / 703 µs |

The `jobs` workload on a four-thread pool shows none of it (3 of 300), which points at concurrent file reads on that
kernel rather than the pool, and no arm or binary differs, so it is not a diagnostic cost; at four threads a first Linux board was bimodal and judged
disabled over and basic unresolved on noise alone. No strace or perf runs on this host to go further.

## Found on the way

`cg_annotate` on those counts: 36% of the program's instructions are one line, `Array<T>::resize`'s
value-initialization loop (`crd/containers/array.hpp`), about two instructions per byte when `read_file_binary`
grows its output from a 16 KiB to a 256 KiB file. A `u8` store may alias the `m_data` member, so the compiler reloads
it each iteration and never forms a `memset`. A change to that header rebuilds nearly every unit and moves every
board, so it is the next batch (below), not this one.

## Tests and teeth

The three `crd-diag-overhead-io-*` CTests hold the structural half (`--check`). Teeth on win-debug, each restored,
rebuilt and rerun green: a site count one above the reads (basic: "not every site and frame was filtered"; full: "not
every payload was evaluated once"), a range read one chunk off ("a frame computed the wrong answer" in all three
modes) and a dropped `jobs::wait` (the counter pool's shutdown assertion).
