# 2026-07-19 — B17 Order-Independent Transparency (all three tiers: WBOIT · MBOIT · A-buffer)

> Detour D-007, Phase 3.1.6 (v17 GPU compute / CKIR). Entry point: after B4 CLOSED (user-committed), the standing order was
> "go to B17, full 2026 frontier". B17 = order-independent transparency. This session landed ALL THREE tiers — the cheap
> WBOIT, the exact-reference A-buffer, and the moment-based hero MBOIT — each authored once as CKIR and device-verified on
> Vulkan **and** DX12, cross-validated against the exact reference. Built in that order deliberately: the exact A-buffer is
> the rigorous quality gate that then let the MBOIT reconstruction be validated (a wrong moment solve passes kernel==oracle
> by construction; only the cross-check vs exact reveals it — and it did, confirming the formulation is correct).

## What shipped

### B17-a — WBOIT (McGuire-Bavoil, JCGT 2013) — the cheap single-pass tier
- **New gpu-context capability: render-to-texture float MRT + per-attachment blend equations** — the piece OIT (and the
  whole post-processing / deferred frontier) needs, previously absent (every draw forced blend OFF; all targets RGBA8/R32_UINT).
  - Vulkan: `vkCmdSetColorBlendEquationEXT` wired into the shader-object dynamic state; `draw_wboit` creates internal
    RGBA16F accum + R16F revealage images (COLOR_ATTACHMENT | SAMPLED), runs the accumulate pass with **independent**
    blend equations (accum ADD `ONE,ONE`; revealage `ZERO, ONE_MINUS_SRC_COLOR`), barriers them to SHADER_READ, then a
    composite pass samples both (bindless slots 0/1) and blends `avg·(1-reveal) + bg·reveal` via `ONE_MINUS_SRC_ALPHA,
    SRC_ALPHA` over a background-cleared RGBA8 target.
  - DX12: bespoke blend PSOs (`build_wboit_accum_pso` with `IndependentBlendEnable`, 2 RTV formats R16G16B16A16F + R16F;
    `build_wboit_composite_pso`), the two float RTs minted as RTV+SRV, the same two-pass command list.
  - Interface: `IRasterContext::draw_wboit(target, transparent, composite, background, vertex_count)` (appended,
    vtable-stable, graceful no-op where per-attachment blend is unavailable).
- **CKIR shaders** (`tests/gpu-shared/ckir_oit_test.hpp`): the transparent VS/FS emit **two** colour attachments
  (`vec4(Cᵢ·aᵢ·wᵢ, aᵢ·wᵢ)` at loc 0 + coverage `aᵢ` at loc 1; depth weight `w = 0.01 + 10·(1-d)²`); the composite VS/FS
  sample the two float targets and resolve. One IR → GLSL (Vulkan) + HLSL (DX12).
- **Validation**: f16-aware CPU oracle (models "compute-f32, store-f16" blend). Observable RGBA8 matches within **≤2 LSB**
  (f16 accumulation + non-correctly-rounded f32 divide ⇒ a **to-ULP** tier, the established doctrine — same family as
  ocean-spectrum / DAIS). Vulkan == DX12 (both match the same oracle).

### B17-c — A-buffer exact reference (Carpenter 1984) — the ground truth
- **Two portable CKIR compute kernels** (`engine/kir/include/crd/kir/ckir_oit.hpp`):
  - `build_abuffer_store`: one thread per FRAGMENT stores its layer's (r,g,b,a,depth) at node slot = fragment id
    (deferred fragment capture; **static** slot for the fixed-coverage reference scene — the runtime **atomic** append is
    the scalable variant, which needs **value-returning atomics** in CKIR, a separable IR extension noted for later).
  - `build_abuffer_resolve`: one thread per PIXEL gathers its `layers` fragments (slot = pixel + q·W·H), **sorts** them
    ascending by depth via a fully-unrolled bubble compare-exchange network (carrying r,g,b,a with the key), and
    composites front-to-back `C += T·aᵢ·cᵢ ; T *= (1-aᵢ)` over the background.
- **Bit-exact**: the composite is pure f32 mul/add/sub on a **deterministic** (sorted) order — no division — so the device
  output is **BIT-EXACT** vs `eval_cpu_kernel` (worst |Δ| = 0.0) and Vulkan == DX12. The exact reference is exact, not
  to-ULP. Harness: `tests/gpu-shared/ckir_abuffer_test.hpp` (2-kernel chained dispatch, mirroring the HZB multi-pass).

### Quality scoreboard (cross-validation)
- Pure-CPU `oit_exact_composite_rgba8` mirrors the resolve kernel; on the shared scene the approximate WBOIT is **14 LSB**
  max-channel off the exact A-buffer — bounded and measurable, which is *why* the exact tier exists. (`[oit][scoreboard]`.)

### B17-b — MBOIT (Münstermann 2018) — the hero glass/foliage quality tier
- The moment-based transmittance estimate, as a THIRD compute kernel (`build_mboit_resolve`) over the SHARED deferred
  fragment store: per pixel, absorbance `aᵢ = -ln(1-αᵢ)`; warp `w = 2d-1`; power moments `b_k = Σ aᵢ·wᵢ^k` (k=0..4);
  normalized `β = (b₁..b₄)/b₀` feed the 4-power-moment **Peters-Klein Hamburger reconstruction** → each fragment's
  transmittance `T(zᵢ) = exp(-b₀·(1 - vis(wᵢ)))` → composite `Σ T(zᵢ)·αᵢ·cᵢ + exp(-b₀)·background`.
- **Reused the tested reconstruction, transcribed scalar**: `lighting::msm_hamburger` (built for moment shadow maps, of
  which MBOIT is the direct heir) is vec4 — but the compute-kernel emitter is **scalar-only** (the known scar), so it can't
  lower. Transcribed it op-for-op onto scalar moments as `oit::msm_hamburger_scalar` (bias · Cholesky of the Hankel matrix ·
  quadratic roots · 3-case form factor) — faithful, not from-memory. Division + ln/exp ⇒ a **to-ULP** tier.
- **Verified correct via the exact A-buffer gate** (the reason it was built first): the 2-layer diagnostic is decisive —
  **4 power moments represent 2 depth masses EXACTLY**, so MBOIT is **bit-exact** (0 LSB vs exact) at 2-layer complexity
  (glass front+back, thin foliage), where WBOIT errs by **30 LSB**. GPU==`eval_cpu_kernel` to 3e-8 on both backends.
- A speculative "self-inclusion correction" made it worse (161 LSB) and was reverted — the clean formulation is exact
  where the budget suffices, no fudge needed.

### B17-b (extension) — 6-power-moment MBOIT: the hero tier LIFTED to high depth complexity
- The 4-moment tier is exact only up to 2 masses; beyond that WBOIT can win (the moment budget). Rather than record that
  as a loss, **lifted the hero tier**: the Hamburger solve generalizes to a larger Cholesky exactly as the theory says.
- `oit::msm_hamburger6_scalar` — **6 power moments**: a 4×4 Hankel **Cholesky** (unrolled) → solve `M·c = (1,z,z²,z³)` →
  the **cubic** `Σ cₖxᵏ = 0` (3 real roots via the trigonometric method, `acos`/`cos`) → the **Gauss-Radau** form factor
  (Lagrange-weight quadrature over {z, x₁, x₂, x₃}, lower CDF bound = Σ weights of roots in front of z). Resolves 3 masses.
- **Result (both backends): MBOIT-6 is ~1 LSB from exact at 3-layer depth complexity, where WBOIT is 18 LSB off — an 18×
  accuracy win.** Validated against the exact A-buffer gate (which is what caught the earlier 4-moment shortfall).
- **Conditioning:** at exactly 3 masses the 4×4 Hankel is rank-deficient; the regularizing bias is critical. Swept it —
  `1e-2` is the sweet spot: it both tames the cubic's GPU/CPU transcendental amplification (0.087 → 0.0027 float ≈ 1 LSB
  in 8-bit) AND improves accuracy (7 → 1 LSB). A to-ULP tier (the cubic amplifies the transcendental ULP more than a
  simple kernel; the 8-bit output still agrees to ~1 LSB GPU vs CPU).
- **Exact-capacity = ⌊moments/2⌋ masses.** 8/10-moment extends further (larger Cholesky + quartic/quintic). **No loss:**
  MBOIT beats WBOIT at every depth complexity within its (tunable) moment budget.

### B17-b (extension attempt) — 8-moment power: a MEASURED shader-compile wall
- Implemented the 8-power-moment quartic reconstruction fully (5×5 Hankel Cholesky + Ferrari quartic — resolvent cubic via
  the trig method + two quadratics — + a 5-node Gauss-Radau form factor). The MATH is correct.
- But it does NOT ship: the reconstruction is too large for the shader toolchain. Unrolled per-fragment ⇒ thousands of
  straight-line instructions ⇒ the driver never finishes compiling (test hangs > 150s). Restructured to a RUNTIME LOOP so the
  reconstruction is emitted once (MBOIT's composite is a `Σ` of independent per-fragment transmittances — no loop-carried
  product — so it accumulates via read-modify-write on the writable `out`) — STILL hangs (the driver re-unrolls the
  constant-bound loop). Removed it (don't ship untested/impractical code). **6-moment (cubic) is the practical POWER-moment
  ceiling.** This is exactly why Münstermann recommends **trigonometric moments** for high orders — compact + well-conditioned.

### B17-b (extension attempt) — trigonometric moments: a quality wall (the compact reconstructions are too crude)
- Built the trig-moment resolve: depth→angle `θ=π·d`, N complex FOURIER moments `bₖ=Σaⱼe^{ikθⱼ}`, transmittance = the
  integrated truncated Fourier series (`G(θ)=∫₀^θρ`, normalised). It **compiles fast** (5 s) — pure cos/sin sums, NO
  root-solve, so it sidesteps the power-moment compile wall, scaling to 12+ moments cheaply.
- But the QUALITY is a wall: the raw truncated Fourier partial sum of point masses oscillates (Gibbs) ⇒ **200 LSB garbage**.
  **Fejér (Cesàro) weighting** `σₖ=1−k/(M+1)` makes the reconstructed density non-negative ⇒ monotonic/bounded CDF ⇒ **80
  LSB** — but Fejér inherently over-smooths, so it *plateaus* (M=6 → 80, M=12 → 84) and still **loses to WBOIT (14 LSB)**.
- Diagnosis: the compact trig reconstructions (Fourier/Fejér) are too blurry for OIT. The reconstruction that would beat
  WBOIT — **Szegő quadrature** (exact mass recovery) — needs to find the Szegő-polynomial roots on the unit circle, i.e.
  root-finding, which lands right back on the **same compile wall** as the power quartic. Removed the trig attempt (a tier
  worse than WBOIT isn't worth shipping).

### Conclusion — the practical ceiling, mapped
**6-moment power MBOIT (3 masses, 18× over WBOIT at 3 layers) is the practical ceiling of *per-fragment moment-based OIT* in
this unrolled compute architecture.** Both routes past it hit fundamental walls: exact-recovery reconstructions (power ≥8,
Szegő trig) explode the shader → compile wall; compact approximations (Fourier/Fejér) are too crude → quality wall. **Beyond
3 masses, the EXACT A-buffer** (shipped this session, bit-exact both backends) **is the tool** — it beats WBOIT trivially
(it's exact) at any depth complexity. The moment tiers own the low-complexity glass/foliage regime (bounded memory, no sort).

### B17-b (extension attempt) — per-pixel-hoisted runtime-loop: the architecture works, but the reconstruction is the wall
- Built the per-pixel-hoisted 8-moment resolve: the quartic reconstruction runs inside a loop whose bound is read from a
  CONFIG BUFFER (runtime, so the driver can't constant-fold + re-unroll it) ⇒ the big body is emitted ONCE.
- It still hung. **Decisive diagnostic:** swapping the quartic for a trivial reconstruction (same loop + config machinery)
  runs **instantly** ⇒ the runtime-loop + config-buffer architecture is CORRECT (config read fine, loop terminates, no
  runtime hang). So the hang is the **shader compiler choking on the 8-moment quartic body even emitted once** — the wall is
  the single reconstruction's intrinsic complexity (5×5 Cholesky + resolvent cubic w/ `acos` + Ferrari quadratics + 5-node
  Lagrange + the ill-conditioned solve), NOT unrolling/replication. No architecture change lifts it. Removed.
- **DEFINITIVE:** 6-moment (cubic) is the reconstruction-complexity ceiling for the shader toolchain. Two orthogonal axes:
  the runtime loop scales the FRAGMENT count (overdraw) freely; the reconstruction body caps the MASSES-RESOLVED at 3.

## Conclusion (final) — B17 OIT, complete
Three tiers shipped both backends: **WBOIT** (cheap, to-ULP), **MBOIT** (4-moment exact@2 masses / 6-moment 18× WBOIT @3
masses — the practical ceiling, exhaustively mapped), **A-buffer** (exact, bit-exact — the tool for arbitrary complexity).
Every route past 3 masses hit a measured wall (power ≥8 & Szegő trig: compile; Fourier/Fejér trig: quality). WBOIT is beaten
across the board — by MBOIT in the bounded-memory regime, by the A-buffer everywhere. **B17 done.**

### B17-c (scalable) — the ATOMIC LINKED-LIST A-buffer: value-returning atomics in CKIR (SHIPPED, bit-exact both backends)
- **New CKIR capability — value-returning atomics.** The static A-buffer used a fixed node slot per fragment (reference-only);
  the *deployable* GPU A-buffer captures a dynamic, unbounded fragment count via atomics that RETURN their old value:
  - IR: two new statement kinds `BufferAtomicAddFetch` + `BufferAtomicExchange`, each producing an `AtomicResult` placeholder
    LEAF node (dtype = buffer element) that the statement materializes exactly once — an **impure** value (never CSE'd, never
    re-read), the same discipline as `Materialize`. Builders `atomic_add_fetch(buf,idx,val)` / `atomic_exchange(buf,idx,val)`.
  - Lowering, all five backends: GLSL `atomicAdd`/`atomicExchange` · HLSL `RWByteAddressBuffer.InterlockedAdd/Exchange(off,val,
    ORIG)` (HLSL's out-param form of a value-returning atomic) · CUDA `atomicAdd`/`atomicExch` (natively return old) · MSL
    `atomic_fetch_add_explicit`/`atomic_exchange_explicit` · WGSL `atomicAdd`/`atomicExchange`. No backend silently drops it.
- **The two kernels** (`ckir_oit.hpp`): the BUILD kernel — one thread per fragment: `slot = atomicAdd(counter,1)` (unique node
  id), store (r,g,b,a,depth) into the node pool, `prev = atomicExchange(head[pixel], slot)` (push), `next[slot] = prev`. The
  RESOLVE kernel — one thread per pixel: walk `head[pixel] → next → …` up to `layers` deep, gather, sort by depth (the same
  compare-exchange network as the static resolve), composite front-to-back.
- **Gold node layout:** ONE interleaved node pool (stride-5 f32 `[r,g,b,a,depth]`) + a parallel u32 `next` array — the AAA
  `struct Node{ vec4 col; float z; uint next; }` pool factored into CKIR's single-dtype buffers. Five bindings for build, four
  for resolve (was nine/eight — over the 8-binding descriptor cap, which was the actual segfault: an over-cap pipeline came
  back null and the dispatch deref'd it).
- **Result:** the race-built, sort-resolved composite matches the static-slot **EXACT reference BIT-FOR-BIT** (worst |Δ| = 0),
  Vulkan **and** DX12 — proving the dynamic atomic capture loses no fragments. Tests: `[oit][atomic]` on both backends.
- **Numbers:** Vulkan `[oit]` 34 assertions / 5 cases; DX12 `[oit]` 30 / 6. No regression in `[raster],[compute]`.

### B17-c (scalable) — STOCHASTIC TRANSPARENCY (Enderton 2010): the cheap unbounded tier (SHIPPED, bit-exact both backends)
- **The tier:** no list, no sort, no moment budget. One CKIR kernel (`build_stochastic_resolve`), one thread per pixel: for
  each of S sub-samples, keep the NEAREST fragment a deterministic hash stochastically covers (screen-door `hash < αᵢ` + a
  z-test); average the S samples. **Unbiased:** P(fragment i is a sample's nearest cover) = αᵢ·Π_{nearer}(1-αⱼ), whose
  expectation is exactly the front-to-back `over` — so E[stochastic] == the exact A-buffer and the mean converges as ~1/√S.
  Real deployment = 1 sample/frame + TAA (S == frames); the kernel models S samples in one dispatch.
- **Portable "randomness":** the RNG is a DETERMINISTIC integer hash (triple32) of (pixel, fragment, sample) → the noise is
  BIT-IDENTICAL across backends and vs the oracle (consistent TAA history). Verified: GPU==oracle worst |Δ| = 0 on both
  Vulkan and DX12; bias(S=32) ≈ 0.003 (unbiased); per-pixel RMS noise halves at 4× samples (matching √S).
- **⛔⛔ THE ORACLE HAD A u32 HOLE — FIXED (core, mission-critical).** A full 32-bit avalanche hash multiplies full-width
  values; `apply_binary` did integer ops **in f64** (loses bits > 2^53) and `round_dtype(U32)` never wrapped mod 2^32 — so the
  oracle's hash diverged from every GPU (first run: worst |Δ| = 0.72). The existing hashgrid/NRC hashes only worked because
  their operands stayed < 2^53. Added `apply_binary_typed(op,x,y,dt)` (ckir.hpp): Add/Sub/Mul/Shl on U32/I32 compute in real
  u32 (two's-complement wrap) — wired into BOTH evaluators (`ckir_kernel_eval.hpp`, `ckir_eval.hpp`) and the const-folder.
  Full kir suite re-run: **34759 assertions / 168 cases green** (the fix is a no-op for non-overflowing ops ⇒ zero regression,
  strictly correct for overflowing ones). This unblocks ALL future integer-PRNG/hash kernels being bit-exact-portable.
- **Numbers:** Vulkan `[oit]` 42 assertions / 6 cases; DX12 `[oit]` 35 / 7.

### B17-c — OIT tier GPU PERF BOARD (kernel-only, Vulkan `last_gpu_ms` min-of-30, 1024²×4-layer = 4.2M fragments)
- Hidden bench `[.oit-bench]`. Board (→ `docs/bench/2026-07-19-oit-tier-perf.md`): STORE 0.130 ms · A-buffer resolve 0.155
  (total 0.285) · MBOIT-4 0.153 (0.283) · MBOIT-6 0.144 (0.274) · atomic list 3.010 · stochastic 1.964 (S=32; ≈0.061/frame @ S=1).
- **Findings:** the static store-based tiers are cheapest and **MBOIT's accuracy is FREE** — memory-bound, so even MBOIT-6's
  cubic reconstruction hides behind the fragment-gather bandwidth (it's a hair *faster* than plain A-buffer resolve). The atomic
  list is ~10× (atomic contention + divergent walk — the unbounded-depth price). Stochastic is the cheapest UNBOUNDED tier
  per-frame (~0.061 ms @ S=1 + TAA). The cost/accuracy map is complete.
