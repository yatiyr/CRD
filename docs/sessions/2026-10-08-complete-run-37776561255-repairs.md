## Causes and changes

1. **gcc `-Werror=unused-result` in `crd-ceridc-tests`** (linux-gcc-release, linux-gcc-relwithdebinfo,
   linux-gcc-shipping). `tests/tools/ceridc/test_ceridc_diag.cpp` ran the granted `capture.start` with
   `(void)std::system(cmd)`. glibc marks `system` `warn_unused_result` when fortify is on (the optimized lanes), and gcc
   does not accept a `(void)` cast as using the value. The exit code is now kept and checked against the report:
   `ceridc` exits 0 exactly when the report says `"ok":true` (`emit` in `tools/ceridc/src/main.cpp`), so the case now
   also checks that.
2. **`diag 8b: the sandbox frame loop keeps ticking while its program runs, then pauses and cancels it`**
   (win-shipping, win-clang-cl-shipping; `REQUIRE(frames.idle(panel, 20U))` failed). The test started
   `inspect_demo`'s `main` with 2^31 - 1 loop iterations and expected 20 idle frames while it ran. An inspected run
   keeps its step budget (`plan::run`'s 2^24 steps; the design says "Cancel and the fuel budget are preserved"), so the
   run ends with `FuelExhausted`. Measured in win-shipping: the run ended after 100-102 ms (5 of 5 runs, `err=4`). The
   hosted Windows runner sleeps about 15.6 ms per 1 ms frame sleep, so 20 frames (about 300 ms) always outlasted it;
   locally (about 1.5 ms per frame) the later `request_pause` failed `NotRunning` in 4 of 150 runs. The budget is the
   documented contract, so the test changed, not the engine:
   - The frame-loop claim is checked over one whole run: every frame until the run ends returns `None` and stays
     under the frame bound, at least one frame ticks while the program runs, and the run ends `Failed` with
     `FuelExhausted`. A fixed frame count that a fast build can outlast is no longer assumed.
   - The pause is requested as soon as the run's thread attaches (`pause_when_running` retries only `NotRunning`,
     yielding). A pause lands at the next safe point, which can still be before the loop. Such a stop is continued
     and the pause requested again until a stop lands in the loop. Each round runs at least the held instr, so this
     ends within a few rounds (bounded at 64) and does not depend on timing. The stop checks (reason `PauseRequest`,
     depth 0, a loop line, the call's value 36) and the cancel checks are unchanged.
3. **`sample ring: reader contention is exact and actually occurs under load`** (win-shipping-profile;
   `refused=0 succeeded=8000`). Reproduced locally in `build/win-shipping-profile`: 5 of 100 runs saw no refusal. A
   worker's 1000 copies of a 1024-sample window can fit in one scheduler quantum, so the workers can run one after
   another and never overlap. Following the test's own rule (raise the load, never drop the `REQUIRE`), each worker now
   makes at least its 1000 copies and then keeps copying until some copy has been refused or 10 s pass. The accounting
   counts every attempt (`refused + succeeded == attempts`, `attempts >= 8 x 1000`), the exactness and `bad_*` checks
   are unchanged, and `REQUIRE(contended >= 1)` stays.
4. **`the SPSC command ring: cross-thread order and completeness`** (linux-clang-tsan; `99872 == 99871`). The
   consumer loop was `if (try_pop) { check } else if (done && !try_pop) { yield }`. When the first pop found the ring
   empty, the producer then pushed its last commands and set `done`, and the second `try_pop` succeeded, that command
   was popped and never checked, so the next payload was one ahead. The `REQUIRE` then threw on the consumer thread
   while the producer `std::thread` was still joinable, which called `std::terminate`; TSan reported the signal
   handler's allocation. Now every popped command is checked, an empty ring only yields, the first out-of-order payload
   stops the drain, the producer stops waiting once the consumer stops (`abandon`), and the assertions run after the
   join.
