## Causes and changes

1. **`scripts/test-diag-coverage.py`: 11 failures and 1 error on every Windows runner** (the repository step and
   `crd-diag-coverage` on all Windows lanes; for example "scope file src/a.cpp is not instrumented on this lane").
   `export_files` matched llvm-cov file names only against `Path(source_root).resolve()`. The hosted runner's
   temporary directory is an 8.3 short name (`C:\Users\RUNNER~1\...`). `resolve()` expands that name, but the
   synthetic export names the files under the root exactly as given, so nothing matched. A real coverage build
   whose source root reaches the compiler through a short name or a symbolic link fails the same way. Reproduced
   here by pointing `TEMP` and `TMP` at the short name of a new directory (`LONGTE~1`), which gave the same 11
   failures and 1 error. The evaluator now accepts both the root as given (made absolute) and its resolved form. A
   new case names the files under a root with a `..` step and under its resolved form. It fails on the old evaluator
   and passes on the new one.
2. **`diag10c: the resident reading follows memory this process touches`** (every hosted Linux lane;
   `after.resident.high_water >= peak`: 72708096 >= 72777728, 17 pages short). On Linux, `read_host_memory` reported
   `max(VmHWM, VmRSS)` for each call. The kernel sums VmRSS approximately from per-CPU counters, and it records VmHWM
   from such a sum only at some points (when the mapping shrinks). So a later VmHWM can be lower than a VmRSS that an
   earlier reading already reported, and the peak was not monotonic. The failure did not reproduce on this host's WSL2
   guest (kernel 6.6, 32 CPUs, 200 runs before the fix). The 4-vCPU hosted runner shows it. The engine now keeps a
   process-wide peak (an atomic maximum, no allocation) and reports it, on Windows too, so the peak cannot fall
   between readings by construction. The header states this. The `CHECK` is unchanged. A new case runs eight map,
   touch and release cycles and requires the peak never to fall across any of the sixteen readings. It is recorded in
   the [nonreproduced-failure register](../../tests/support/diag/nonreproduced-failures.json), because the mechanism
   is inferred and was not observed here.
3. **Four module-identity cases on win-release only** (`live modules: the enumeration names this executable ...`,
   `flight trigger: the fatal path in a child process ...`, `diagnostic host: a frame hitch ...`, `diagnostic host:
   an application that fails on purpose ...`). Plain Release links without debug information: `CrdBuildProfiles`
   keeps `/Zi` out of non-shipping Release, and `CMakeLists.txt` adds `/Zi` and `/DEBUG:FULL` only to Shipping. So
   the images have no CodeView record. `dumpbin /headers` of win-release's `crd-perf-tests.exe` shows a 0x1C-byte
   debug directory with no `cv` entry, while win-debug's shows `Format: RSDS`. With no record, the engine reports
   `id_kind None`, and `identity_matches` refuses, as the contract requires ("refuse, don't guess"). The cases assumed
   that every Windows image carries a PDB record. All four reproduced in `build/win-release`. The cases now branch on
   what the file on disk carries, read by the independent parser in `module_file_identity.hpp`:
   - The file carries a record (every other Windows lane, and every Linux build through its GNU build-id): the
     previous checks hold, and the live-walk case also requires `identity_matches` against the file.
   - The file carries no record: the live walk and the bundle must report `None` with a nonzero PE timestamp and no
     debug file, and `identity_matches` must refuse.
   In both branches `same_identity` compares every field (kind, id bytes, age, size, timestamp, checksum). Linux
   lanes require a GNU build-id. Giving CodeView-less images the `PeImage` identity, or building win-release with a
   PDB, would also make these cases pass. Both change a design or a lane configuration, so neither was done here.
4. **clang-tidy `misc-unused-alias-decls`** in `tests/support/diag/specimens/flight_fatal_specimen.cpp`. The
   `namespace cont` alias was written for `CRD_DIAG_INVARIANT`, but the macro names `::crd::containers::StringView`
   fully, so the alias is removed. The tidy lane stopped at 2323 of 2376 steps, and none of `crd-perf-tests`' 50
   test files were analysed. All 50 and the specimen are clean under `tidy-files.py`. The diag-consumer package
   sources are not part of that build graph.
5. **`CEIR-17d GATE ... (Vulkan)` on linux-clang-tsan**: a TSan data race between two lavapipe `llvmpipe-N` worker
   threads. One thread's `operator new` (from `llvm::allocate_buffer`) races another's `operator delete` on the same
   block. Both access stacks hold only TSan's allocator interceptors and `libLLVM.so.20.1`. `libvulkan_lvp.so` appears
   only in the thread-creation stacks (under `vkCreateDevice`), and TSan does not match suppressions against those,
   so the existing `race:libvulkan_lvp.so` could not cover it. Mesa links LLVM for lavapipe's JIT; nothing in Cerid
   links LLVM. `race:libLLVM.so` is added to `tests/support/diag/tsan-suppressions.txt` with the reason, following
   the file's rule: only third-party libraries that are not built with TSan. The race did not reproduce here: through
   ctest on WSL linux-clang-tsan (Mesa lavapipe), the gate passed 60 of 60 runs with the previous suppression file and
   60 of 60 with the new one, with no TSan report. The case is recorded in the register as nonreproduced.
