## crd::math gap-fills — native, bit-exact (per the user's "implement ourselves" mandate)

Audited `crd::math` vs `<cmath>` and filled the genuine gaps NATIVELY (own logic — bit-ops + composition of the exact primitives,
no `std::<fn>` passthrough), all in `select.hpp`: **signbit** (bit test), **fmax/fmin** (IEEE maxNum/minNum, NaN-dropping),
**fdim**, **rint** (round-ties-to-even from trunc/abs/copysign), **nearbyint** (now native = rint, was a std passthrough),
**modf** (sign carried via copysign — `modf(-100,·)=-0.0`), **frexp** (IEEE bit surgery, subnormals via a 2^54 scale), and
**remainder** (see below). New `tests/math/test_select.cpp`: **BIT-EXACT vs std across ties/±0/subnormals/NaN — 3380 assertions**;
full math suite 6428/162, tidy-clean (also de-nested a pre-existing `clamp` ternary → `min(max())`). **`remainder`** was first
deferred (the naïve `x − y·rint(x/y)` isn't bit-exact — 202 mismatches from rounding + the −0 sign), then **implemented correctly**
on request via the **fdlibm reduction**: `r = fmod(|x|, 2|y|)` then reduce into `[−|y|/2, |y|/2]` (ties-to-even fall out of the
mod-2|y| step; each subtraction is exact by Sterbenz). Two scars fixed en route — the sign is `signbit(x)?-r:r`, NOT `copysign(r,x)`
(remainder is odd in x, `remainder(5.5,2)=-0.5`), and tiny/zero `|y|` needs the `r+r` comparison (`0.5*|y|` underflows). Special
cases (`y==0`, `±inf`, NaN) resolve for free through `fmod` semantics — no guards. The IEEE-exact
single-instruction ops (floor/ceil/round/sqrt/fma → ROUNDSD/SQRTSD/VFMADD) stay as std by design — reimplementing is slower for
identical bits, and the module's own doctrine is "correctness is exactness."

## D3 — the variant / permutation system

`engine/shader-cook/{include/crd/shadercook/variant.hpp, src/variant.cpp}`. A shader is an übershader with feature toggles; a
VARIANT is a `key` bitmask.

- **`VariantBuildFn(g, key, user) → KEntry`** — the caller builds the kernel for a key, emitting only the LIVE path. This is how
  real material compilers cook per-permutation, and it's the honest fit here: `KGraph::stmt(i)` is const-only and there's no graph
  copy, so in-place kernel specialization (pin-option + DCE the body) isn't cleanly supported without kir surgery — the per-key
  builder sidesteps it and stays general (a builder may itself call B7 `specialize()` on an übergraph).
- **`cook_variant_matrix(build, keys[], opts) → VariantMatrixResult`** — cooks the requested keys, content-hashes each specialized
  IR (`ResourceId::from_content`), and **DEDUPs** identical hashes (the cook's own content-hash cache makes a deduped key a cache
  hit — cooked once). Returns the manifest (key → bundle hash) + **telemetry** (`requested` vs `unique` = the permutation
  reduction). ON-DEMAND: only the requested keys are cooked.
- **`cook_one_variant(build, key)`** — a single on-demand variant.

**`[variant]` gate:** 4 keys where bit0 scales the output (×1/×2) and higher bits are DEAD → `requested=4 unique=2` (a 50%
permutation reduction); the dedup is proven at the hash level (`key0==key2`, `key1==key3`, `key0≠key1`); and each on-demand
variant's cooked SPIR-V runs GPU-correct (scale ×1 and ×2). 271/13 smoke green (cook/variant/dgc/coopvec/program), tidy-clean.

### Honest scope

- The dedup + on-demand + telemetry + GPU-correct-per-variant is the load-bearing value and it's verified.
- The variant space is a per-key builder (library API — the engine's shader registry calls it), not a `.kgph`-driven CLI flow,
  because specialization is a construction concern, not a serialized-graph transform. A single multi-variant container file
  (variants as sub-resources of one `.crdr`) folds in with D4's runtime load.
- **Next: D4** — runtime load + pipeline cache (load the cooked bytecode for the running backend+variant; `VkPipelineCache` /
