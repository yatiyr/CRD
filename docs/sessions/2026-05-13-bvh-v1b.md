# Session — 2026-05-13 — Phase 3.1.7 v1b: `bvh_refit` (O(n) bottom-up BVH refit)

## Goal

Second `crd-geometry-bvh` slice: `bvh_refit` — recompute every node's bounds
from the current primitive AABBs without rebuilding the tree's topology, for
dynamic scenes where the set of primitives is fixed but their boxes move each
frame. Catto GDC 2019.

## What we built / changed

- **`src/aabb_ops.hpp`** (new, internal — lives under `src/`, not `include/`):
  the rounding-free AABB accumulation primitives (`aabb_empty`,
  `aabb_include_point`, `aabb_merge`, `aabb_centroid`, `aabb_half_area`,
  `component`, `bounds_of_range`) in `crd::geometry::bvh::detail`, extracted out
  of `bvh_build.cpp`'s anonymous namespace so the builder and the updater share
  one copy. `bvh_build.cpp` now `using detail::aabb_*;` instead of its own
  definitions.
- **`include/crd/geometry/bvh/bvh_update.hpp`** (new, public): declares
  `bvh_refit(BvhTree& tree, ConstSpan<AABB3<f32>> prims)` (and reserves the
  spot for v1c's `bvh_insert` / `bvh_remove`). Added to the umbrella `bvh.hpp`.
- **`src/bvh_update.cpp`** (new): `bvh_refit` — a single pass over the node array
  from the last node to the first. This is bottom-up because `bvh_build` always
  pushes a node before its two children, so a node's children always have a
  higher array index (a `CRD_ASSERT` checks `left_first > ni` on each interior
  node). For a leaf, `bounds` = union of `prims[prim_indices[…]]`; for an
  interior node, `bounds` = union of the two children's (already-refit) bounds.
  Topology — the node array structure, the leaf-order permutation, every
  `split_axis` — is left untouched; only `bounds` is rewritten. No-op on an
  empty tree; `CRD_ASSERT` on a prim-count mismatch (the caller must pass
  `prims` with the same length as the original build — changing the count is
  undefined, rebuild instead).
- **`tests/geometry-bvh/test_bvh_refit.cpp`** (new, 4 cases): (1) refit with the
  same prims leaves the tree byte-identical to a fresh build (`memcmp` of node +
  index arrays); (2) after translating every box — some by a little, some far
  enough to leave their old leaf entirely — every leaf's bounds equal the exact
  union of its prims, every interior's equal the union of its children, the root
  encloses every moved box, and `bvh_raycast` / `bvh_overlap` against the moved
  set still match a brute-force reference (correctness is independent of how far
  things moved); (3) the topology is untouched — `node_count`, `root`,
  `prim_indices`, and every node's `left_first` / `prim_count` / `split_axis`
  are byte-for-byte unchanged after a refit; (4) empty tree is a no-op,
  single-leaf recomputes that leaf's bounds.

## Plain-English explanation

When physics objects move every frame, rebuilding the whole BVH from scratch is
wasteful — the *shape* of the tree (which object is grouped with which) usually
stays good even after small movements. `bvh_refit` walks the tree from the
leaves up and re-fits each node's box around its (now-moved) children. It's
O(n), allocates nothing, and never touches the tree structure — so it's the
per-frame update path. Correctness is guaranteed regardless of how far things
moved (an object that drifted out of its old group just makes its ancestors'
boxes bigger, so a ray still finds it); only *speed* slowly degrades, and when
it degrades too much the caller does a full rebuild instead. Incrementally
inserting/removing objects (with tree rotations to keep quality) is v1c.

## Decisions made

- Refit relies on the build invariant "a node's children have a higher array
  index than the node" — guaranteed by `bvh_build`'s push order, asserted in
  debug. (Documented on `bvh_refit`.)
- The shared AABB scratch ops live in an internal `src/aabb_ops.hpp`
  (`crd::geometry::bvh::detail`) rather than being duplicated per TU. Future
  `-bvh` updaters (v1c) use it too.
- `bvh_update.hpp` is the home for in-place mutations (refit now; insert/erase
  in v1c) — kept separate from `bvh_build.hpp` ("building") and `bvh_query.hpp`
  ("reading").
- Note (per the standing directive that geometry sub-modules use our own / the
  best-available allocators): the geometry APIs take `IAllocator*`; `bvh_refit`
  allocates nothing, and `bvh_build`'s transient working scratch (centroids,
  partition scratch, build stack) currently shares the tree's allocator — a
  later refinement could let the caller pass a separate scoped/linear scratch
  allocator (matters most when v1f's jobs-parallel build needs per-thread
  scratch). Not blocking; captured here.
