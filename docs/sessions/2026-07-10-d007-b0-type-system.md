## The arc

**B0-0 — a real bug in `KGraph::optimize()`, found while orienting.** The DCE reachability walk pushed the 4th operand
`d`, and the CSE hash-cons both hashed and compared it — but the compaction loop that renumbers operands only remapped
`a`/`b`/`c`. Any graph containing a `mat4()` (the only op that sets `d`) that went through `optimize()` kept a **stale
index into the pre-compaction array**: a silently wrong 4th column, or an out-of-bounds read once the graph shrank past
it. Latent only because `optimize()` is called from exactly one test and no mat4 graph ever reached it — Phase D's cook
runs `optimize()` on material graphs full of mat4.
Fixed at the root, plus `KGraph::operands_valid()` (a structural invariant: every operand references a strictly earlier
node, because push order *is* topological order) asserted at the end of `optimize()` via `CRD_ASSERT`. Verified
`CRD_ENABLE_ASSERTS 1` in win-debug so the guard is genuinely live, and verified the new regression test **fails on the
unfixed code before fixing it** (SANITY #2 — the first two TLSF regression tests were theater because they passed on the
buggy code too).

**B0-1 — `KType`: one composed type, replacing `(dtype, comps)`.** `KNode::comps` (a `u8`) was doing double duty as
"how many scalars" and "what type". It cannot express B0's contract: `comps == 4` is ambiguous the moment `mat2` exists
(vec4 vs mat2 vs a 4-array), and it carries no scalar type, so `ivec3` / `bvec4` are unrepresentable. Replaced both
fields with `KType {DType scalar; TKind kind; u8 rows; u8 cols;}` — the way SPIR-V (`OpTypeVector`/`OpTypeMatrix`) and
Slang model a type — with `dtype()` / `comps()` accessors so read sites stay legible. The CSE key now hashes the **full**
type (the generalization of the `comps`-in-CSE-key scar from Phase A). Compiler-guided rename across the eval, five
emitters, both GPU backends and the tests; zero behaviour change, proven by the three suites landing on their exact
pre-existing assertion counts.

**B0-2 — `mat2` + non-square R×C, type-aware emitters.** `MatFromCols` / `MatVecMul` / `MatMatMul` / `MatTranspose`
generalized from square-only to (R×C) in the oracle and both emitters. Emitters are now driven by the **type**, never by
a component count. Added `input_mat` (a mat2 input was otherwise unrepresentable, since `input_vec(…, 4)` resolves to
vec4 by the A3 convention).

**B0-3 — comparisons are bool-typed; `bvec` / `ivec` / `uvec`.** A comparison now yields `bool` (scalar) or `bvecN`
(componentwise), the way GLSL, HLSL and SPIR-V define them; the old `? 1.0 : 0.0` is a *lowering* choice a backend may
still make (the tile / CUDA / WGSL emitters do), not the IR's type. Added `DType::U32` (**appended, never reordered** —
a DType is stored in the IR and will be serialized by the Phase-D cook; the vtable-stability discipline applied to an
enum). GLSL emits `vec/ivec/uvec/bvec` and the `lessThan()` family (GLSL has no `<` on vectors); HLSL emits
`floatN/intN/uintN/boolN` and relies on its already-componentwise relational operators. `any`/`all` consume a bvec
directly. A bool stores to a buffer as float 0.0/1.0 — std430 has no `bool` — which is exactly what the CPU oracle
materializes, so **the existing comparison-readback tests kept passing untouched**; the migration cost landed on the
emitters, not the test corpus. `Select` accepts a Bool condition *or* a numeric one (bit-extraction produces numeric
flags in radix/morton; forcing those through a cast would buy nothing).

**B0-4 — fixed-size arrays + structs.** Two design decisions drive it. (1) `KNode` has exactly four operand slots
(`a`/`b`/`c`/`d`) and a struct has N fields, so aggregates carry **variadic operands** in a flat pool on `KGraph` —
the same machinery B4 (mesh outputs), B6 (node library) and B9 (RT payloads) will want. Every operand walk (DCE, the CSE
key, the `optimize()` renumber, the emitters' reachability) must visit them; this is *literally* the B0-0 bug class one
field further out, so `operands_valid()` checks them and `clone()` now hard-asserts rather than copy a pool offset
across graphs. (2) A struct value is lowered by **SROA** — `StructMake`/`ArrayMake` materialize nothing and a
`FieldGet`/`ArrayGet` resolves to the field's temp — which is what Slang and DXC do for value-typed aggregates. That
means **no GLSL/HLSL struct declaration and no std430 layout** in B0-4: buffer-*backed* structs (which do need std430)
are the resource-binding slice, B3, exactly where ADR-0102's frequency-set model already puts them. Aggregates are also
a contiguous run of components in the flat storage vec/mat already use, so the CPU oracle handles the general case
(including a `Select` of structs) while the emitters refuse a non-`Make` aggregate loudly rather than emit something
subtly wrong. Array-ness is a property of any element form (`vec3[2]` is kind=Vec, rows=3, count=2), so there is no
separate `TKind::Array`; a fixed `count` on `KType` carries it.
`array_get` takes a CONSTANT index — a dynamic index needs a real array in memory, not an SSA value, i.e. a
buffer-backed access (B3), not a value-layer one. Stated, not silently omitted.

## Scars / findings

- **⛔⛔ The tidy gate reported "clean" for files it never PARSED.** `scripts/tidy-files.ps1` hand-maintained its `-I`
  list, which omitted whole modules (`engine/kir/include` was never in it). So `#include <crd/kir/ckir.hpp>` failed →
  the TU never parsed → **zero check diagnostics** → and the script *filtered out* `"file not found"`, making a blind
  file byte-identical in output to a clean one. `engine/kir-vulkan/src/backend_vulkan.cpp` passed the DoD gate without a
  single line ever being analysed; **89 violations across `crd-kir` were invisible**. It had three silent-pass holes,
  each found by tripping it: (1) unresolved include; (2) a `.cpp` with no compile-DB entry (Metal/HIP aren't configured
  on Windows) falling back to a bare command; (3) a path that doesn't exist → `SKIP (not found)` → **exit 0** (an
  arg-splatting bug collapsed 27 paths into one string and the whole sweep printed "All passed" while gating nothing).
  Fixed: unresolved include ⇒ loud `UNGATED`; missing path ⇒ `MISSING`; both non-zero exits, never folded into "clean".
  `-I` set now **globbed from `engine/*/include`** so a new module cannot silently fall out. `.cpp` driven from the real
  **compile database**, mirrored to a scratch copy with MSVC's PCH flags (`/Yu`, `/Fp`, `/FI…cmake_pch`) stripped —
  clang cannot read an MSVC `.pch` and un-stripped they masquerade as `clang-diagnostic-error`. The gate now prints the
  file **count** it actually gated: *"All passed" without a count is unfalsifiable.* Same disease as the `#deps 0` ninja
  scar and the `win-tidy-local` `CMAKE_COMMAND` rewrite — **the instrument broke silently and kept printing PASS.**
  (Memory: `feedback_tidy_gate_clean_on_unparsed_files`.)

- **⭐ GLSL is the TYPE-STRICT backend; a DX12-green result proves nothing about IR type correctness.** When comparisons
  became bool-typed, a graph doing `Add(float, cmp_result)` **failed to compile on Vulkan and silently passed on DX12** —
  HLSL implicitly promotes `float + bool`, GLSL rejects it. GLSL also rejects `precise bvec3` (the qualifier is
  float-only) and has no `<` on vectors. An IR-level type mistake therefore surfaces as a Vulkan-only `run() == false`.
  Corollary: fix it in the **IR/test** (insert an explicit `cast`), never by loosening the GLSL emitter to match HLSL's
  permissiveness — the permissive backend is the one that's wrong. This is the second instance of the pattern recorded
  in `feedback_glsl_writeonly_buffer_readback_portability`; that memory now carries the generalized rule.

- **`KOp::Cast` was never implemented in the WGSL / MSL / CUDA emitters.** `is_fusable(Cast)` returns true, but their
  op-switches hit `default: return false` and silently bailed. Invisible until a graph first used a cast. Added to all
  three (each lowers every temp to `f32`/`float`, so a Cast is an explicit conversion there).

- **GLSL `MatFromCols` hardcoded `mat3`/`mat4`**, so `mat2` emitted `mat3(t0, t1, t-1)`. Caught by the B0-2 Vulkan test
  failing on first run — the failure was worth having.

- **HLSL `MatInverse` unconditionally emitted `crd_inv3`**, so a `mat2` inverse was silently wrong; added `crd_inv2` and
  routed by `type.rows`. **HLSL `crd_outer` was `float3x3`-only**, mistyping any non-square outer product; replaced with
  a generic inline form (row `r` of an R×C outer product is just `a[r] * b`).

- **`app_uint(String&, int)` had ~60 callers wrapping the argument in `static_cast<crd::u32>`** — the cast *was* the
  narrowing the check flagged. One root fix (accept any integral type, cast explicitly inside) took glsl 35 → 3 and
  hlsl 34 → 3 diagnostics.

- **`replace_all` on a short identifier corrupts words** — renaming `hn` → `kHistoN` also rewrote the local `shn` into
  `skHistoN`. The `sed \b` scar, in a different tool. Checked-and-reverted immediately; `hm` was then done with exact
  context because `algorithm`, `arithmetic` and `benchmark` all contain "hm".

- **The B0-0 guard paid for itself inside the same session.** B0-4's variadic-operand remap was written correctly first
  try — so the new regression test passed immediately, which proves nothing. Deliberately removing the remap made
  `CRD_ASSERT(operands_valid())` fire *inside* `optimize()` before the test's own `REQUIRE` was even reached. A guard
  that catches a bug class you introduce later is the whole point of writing it; a test you never watched fail is not
  evidence (SANITY #2/#3).

## Decisions taken

- **`KType` is one composed value, not a `(dtype, form)` pair.** A struct has no meaningful scalar type, so splitting
  the type across two `KNode` fields would become a wart the moment B0-4 lands. `kind` extends to `Array`/`Struct`
  (B0-4) and `Sampler`/`Texture` (B2) without touching the CSE key's shape.
- **The tensor layer stays scalar-valued.** Reduce / movement / contraction / indexing operate on tensors of scalars —
  the multi-dimensionality lives in `Shape`; per-element vec/mat values are the A3 *value* layer above it. Documented in
  the builders rather than left implicit.
- **`clang-format` was NOT run over the module.** These files were never format-conformant (HEAD was already 196 diff
  lines on one test file, 1557 on `ckir.hpp`); the dense one-line-per-opcode style is deliberate for a dispatch table.
  Reformatting would bury the real diff. Flagged, not silently done.

## Backend fan-out — WGSL (same session, user direction: "I want backend fan out as well")

Standing mission (`feedback_mission_portable_gpu_compute_all_backends`) is ALL backends; D-007's exit criteria had
called fan-out "(Optional / opportunistic)". The mission wins, and the doc was corrected. **Fan-out runs BEFORE the rest
of Phase B on purpose:** every emitter reaching type parity now means the stage layer (B3) gets added once across a
uniform base rather than retrofitted into WGSL/MSL later — the exact debt pattern this session diagnosed.

**WGSL ✅** — `emit_vec_wgsl` mirrors `emit_vec_glsl` op-for-op, handling WGSL's real divergences (each of which a naive
mirror gets wrong): no `?:` (⇒ `select(false, true, cond)`, note the operand order), no `inverse()` (⇒ emitted
`crd_inv2`/`crd_inv3`), no `outerProduct()` (⇒ column k of an RxC outer is `a * b[k]`), `faceForward` capitalised,
`inverseSqrt`, `matCxR<f32>`, and **no implicit int→float on assignment** so non-f32 results convert explicitly on
buffer write. Dynamic control flow (`For`) is **refused loudly** (`return false`), not silently mislowered — the
body-scoping pass isn't mirrored yet. Gated on **real WebGPU hardware** vs the CPU oracle; ULP-tolerant, never bit-exact
(WGSL has no `precise`). Suites: kir-webgpu 30791 → **30808**.

**Two more real bugs the fan-out flushed out:**
- **`KirBackendCpu::run` — the CPU ORACLE — never supported vec/mat graphs.** It sized input staging and the output
  buffer by `shape.numel()`, ignoring `comps()`: a vec3 input read ⅓ of its data and the output buffer was 3× too small
  ⇒ heap overflow ⇒ SIGSEGV. It survived because every Vulkan/DX12 vec test compares against an *analytic* reference,
  so nothing had ever pointed the oracle at a vector graph. **The oracle was itself un-oracled** (SANITY #4: name what
  your diagnostic can't see). Fixed; the WGSL tests now gate against it.
- **`graph_uses_vec` was defined with EXTERNAL LINKAGE in both `backend_vulkan.cpp` and `backend_dx12.cpp`** — two
  definitions of one symbol, an ODR violation that stayed quiet only because no program links both backends at once
  (a multi-backend runtime would). Hoisted to one `inline` in `ckir_glsl.hpp`; both copies deleted.

**CUDA ✅ — by SCALARIZATION.** CUDA is the odd backend: `float3` exists but carries **no operators**, and there is no
matrix type at all. Rather than emit a vector runtime into every kernel, `emit_vec_cuda` turns a value of `comps`
components into `comps` scalar temps `t<node>_<comp>` and writes every op out componentwise — nvcc's own SROA would
scalarize a struct back into registers anyway, so it costs nothing and keeps the emitted PTX a direct function of the
IR. **B0-4's aggregates come free:** `StructMake`/`ArrayMake`/`FieldGet`/`ArrayGet` emit nothing and a component index
resolves back to its producing scalar at emit time — which even lets CUDA lower a `Select` of two structs, something the
GLSL/HLSL SROA path must refuse. `For` and mat4 det/inverse refuse loudly. Gated on **real CUDA hardware**. Suites:
kir-cuda 79944 → **80599**.

## ⛔→✅ The CPU ORACLE was not f32-faithful for the A3 vec/mat corpus — FOUND, and FIXED (user-approved)

`backend.hpp` documented `KirBackendCpu` as *"computes each op in f64 then rounds to the node dtype, so an F32 graph is
f32-faithful ⇒ IEEE-arithmetic kernels bit-match a GPU f32 kernel."* That held for the **componentwise** ops
(`Add`/`Mul`/`Select`/comparisons all call `round_dtype` per step). It did **not** hold for the **accumulating** A3 ops:
`Dot`, `VecLen`, `Normalize`, `Cross`, `MatVecMul`, `MatMatMul`, `Determinant`, `MatInverse`, `OuterProduct`, the
geometric ops' dot products, quaternions and `Slerp` all accumulated in **f64 and rounded only on store** — unlike
`Contract`, which had always rounded per step (`acc = round_dtype(acc + prod, dtype)`).

So the oracle computed an f64 dot rounded once while any f32 GPU rounds every multiply-add: a ~1 ULP delta in which
**the oracle was the more accurate one, not the kernel wrong**. It explains something nobody had questioned: every
Vulkan/DX12 vec test compares against *analytic* references with tolerances rather than against the oracle. Nobody
*could* have gated bit-exactness against it. **It left ADR-0098's T1 "certified bit-exact core" unreachable for the
whole vec/mat corpus** — i.e. for most of a shader.

**Fixed** (`eval_detail::rnd`, `mat_det`/`mat_minor_det` now take the dtype): every elementary IEEE operation in the A3
corpus rounds to the node's dtype. F64 graphs are untouched (`round_dtype` is the identity there) — the whole 200-assert
CPU suite passed unchanged, first try. **Proof the fix bites:** the CUDA `==` assertions failed with **320 mismatches**
before it and pass after.

**The payoff — the strongest gate any backend in this project has:** the CUDA vec3 (cross + add + normalize), mat3
`mat·vec`, `bvec` and struct-SROA results now assert **bit-exact (`==`) against the CPU oracle**, not a tolerance.
That works because the scalarized CUDA emitter writes the same elementary ops in the same order with `--fmad=false`.
GLSL/HLSL/WGSL cannot be gated this way yet: their `dot()` / `normalize()` / `inverse()` builtins have
implementation-defined internal order, so those suites stay ULP-tolerant until ADR-0098 §5's `float_controls` audit
pins them. That is now a named, bounded gap rather than an unexamined assumption.

**MSL ✅ — gated structurally, and the gate is proven to bite.** MSL is a C++14 dialect and the closest of the four to
GLSL: native `float3`/`float3x3`/`bool3`, componentwise relationals yielding `boolN` (like HLSL), a real `?:`, and the
same column-first `floatCxR` spelling as GLSL/WGSL. Like WGSL it has **no `inverse()` and no `outerProduct()`** ⇒ emitted
`crd_inv2`/`crd_inv3` and column-by-column outer. Metal has no compiler off macOS, so instead of settling for substring
checks I added **`temps_well_formed`**: every `tN` the kernel references must be declared, and `t-1` may never appear —
i.e. exactly the dangling-operand class that GLSL shipped (`mat3(t0, t1, t-1)`, because `MatFromCols` hardcoded three
columns and a mat2's third operand is `-1`). **The checker is itself tested against known-bad sources** (a `t-1` kernel,
an undeclared-`t9` kernel, and a good kernel where `float3` must not masquerade as a temp `t3`) — a structural checker
that has never rejected anything proves nothing. `For` and mat4-inverse refuse loudly and that refusal is asserted.
Compile + bit-exact run remain ADR-0098 §3 **v17-n** (GH-Actions Apple silicon). HIP is **v17-o**.

**Fan-out complete on every backend reachable from this host.** Suites: kir 200 → **234**.

## B3-core started — the stage & I/O model (B3-a landed)

B1↔B3 were **reordered on user direction** after the audit found B1 unbuildable: `dFdx`/`dFdy`/`fwidth`/`discard`/
frag-depth are fragment-stage constructs (`docs/systems/shader-ir-corpus-and-stages.md` tags derivatives `[M]`:
*"not expressible in a plain compute kernel"*), and CKIR was **compute-only** — no stage concept, every emitter
hardcoding `layout(local_size_x = 256)` / `numthreads(256,1,1)`, both GPU backends creating compute pipelines.

**B3-a (green, kir 234 → 254):** `KStage {Compute, Vertex, Fragment}` · `KBuiltin` · three new leaves.
Two design decisions worth keeping:
- **`StageIn` is one op for both a vertex ATTRIBUTE and a fragment INTERPOLANT**, location-indexed, disambiguated by the
  entry point's stage — which is exactly how SPIR-V models it (one `Input` storage class per location).
- **A uniform block is a STRUCT-typed leaf at `(set, binding)`**, its members read with the *existing* `field_get`.
  That reuses B0-4's struct registry rather than inventing a second aggregate, and **`set` IS ADR-0102's frequency
  slot** (0 frame · 1 pass/lighting · 2 material · 3 object). `dset` joins the CSE key, so two blocks at the same
  binding in different sets never hash-cons together.

**Scar caught immediately:** a stage leaf has **no operands**, so `optimize()`'s const-fold sees "all operands constant"
and folds it into a compile-time value — the same class as `Input`/`Iota`, which were already excluded. A vec/struct
leaf is accidentally saved by the `comps() != 1` guard, so the case that *actually* bites is a **scalar** one: a folded
`gl_VertexIndex` means **every vertex is vertex 0**. My first version of the test used a vec4 UBO field and therefore
**passed with the guard removed** — it wasn't testing anything. Rewrote it around `Builtin::VertexIndex` and confirmed
it now fails without the guard. *A guard you never watched fail is not a guard.*

## ⛔ The B3 plan was WRONG — ADR-0103 + detour D-008 (user direction, 2026-07-10)

The plan above proposed gating the raster emitters on `crd::shader::compile_glsl(Stage::Vertex)`. That makes **CKIR
depend on the module that owns GLSL** — the exact inversion ADR-0101 exists to delete ("backend languages are outputs
only; never authored or stored"). The user rejected it: *"crd-shader must not know any glsl or hlsl, gpu context must
handle all of that… we must be able to handle all kinds of shaders from compute to lightings to materials to ray
tracings to mesh shaders to geometry shaders to everything."*

**The plan was not careless — it was faithfully following `ADR-0099 §6`**, an *Accepted* decision reading
"`crd-shader` stays the single shared GLSL/HLSL→SPIR-V/DXIL compiler for both authored and generated shaders." Two
Accepted ADRs contradicted each other. §6 gives way; **[ADR-0103](../decisions/0103-gpu-context-owns-every-gpu-program.md)**
supersedes it and 0099 §6 is now struck through **in place** (a superseded clause the next reader can still follow is
not superseded — SANITY ledger 2026-07-10).

Three leaks measured, not estimated: `crd-shader` exports `compile_glsl`/`compile_hlsl` (**9 call sites**);
`crd::rhi::ShaderModuleDesc::code` is a `ConstSpan<u8>` of **raw SPIR-V in a public header** (**38 `create_shader_module`
sites / 9 files**); and `rhi::Device` + `gpu::IGpuContext` are **two device layers over two `VkDevice`s**. Closing them
touches `rhi`, `rhi-vulkan`, `renderer`, `draw`, `imgui`, `perf` — past D-007's contract, so per D-007's own rule
(*"promote it, don't let it quietly take over the roadmap"*) it became detour
**[D-008](../detours/D-008-gpu-context-convergence.md)** (C0–C4), which **blocks D-007 from B3-c onward**.

## B3-a′ — the stage model, completed to 14 stages ✅

`KStage` shipped in B3-a as `{Compute, Vertex, Fragment}` — narrower than our own
`docs/systems/shader-ir-corpus-and-stages.md` §2, which already specifies task/mesh (primary), tessellation, geometry
(legacy-but-supported) and the six ray-tracing stages. **A 3-value enum bakes a 3-stage assumption into every `switch`
that consumes it, and each such `switch` is a silent `default:` waiting to mis-lower a mesh shader** — the same class as
`MatFromCols` hardcoding three columns (B0-2) and `KOp::Cast` hitting `default: return false` in three emitters (B0-3).

Landed:
- **`KStage` = the 14 SPIR-V execution models**, ordered by pipeline position; `stage_mask::*` sets (`kWorkgroup` =
  compute\|task\|mesh, `kRayAny`, `kRayIncoming`, `kRayHit`); `is_raster_stage` / `is_ray_tracing_stage` /
  `stage_writes_position` / `stage_name`.
- **32 builtins in ONE `builtin_info` table** carrying the type *and* the legal-stage mask together, so the two can
  never drift apart. `builtin()` no longer switches on the builtin to pick a type — the old switch had **no `default:`
  and only 4 cases**, so any new builtin would have silently defaulted to `f32` scalar.
- **`entry_valid(g, entry, &why)`** — a graph carries no stage, so `builtin()` *cannot* reject `gl_FragCoord` in a
  vertex shader; only an entry knows. Without this the per-stage table is a comment. It also enforces
  position-required-iff-the-stage-writes-one (a vec3 position is the classic bug — `w` is the perspective divide),
  frag-depth-is-fragment-only, unique output locations, unique input locations, and no `StageIn` in a compute entry.
  Reason strings are threaded out, because "the graph is invalid" is not a diagnosis.

**Gate bites:** `FragCoord` in a vertex entry is rejected with the exact reason; the *same graph* is valid as a fragment
entry. Suites: **kir 400 assertions / 43 cases**, `v17` ctest **122/122**, ckir.hpp tidy-clean.

## Honest scope boundaries (stated, not silently omitted)

- **`array_get` takes a constant index.** A dynamic index needs a real array in memory, not an SSA value — that is a
  buffer-backed access, i.e. B3.
- **The GPU emitters require an aggregate to come from a `Make` node.** A `Select` of two structs would need a real
  GLSL/HLSL struct type; the emitters return false (a loud `run() == false`), they do not guess. The CPU oracle is
  fully general.
- **No std430 struct layout.** SROA'd value aggregates never reach a buffer. Buffer-backed structs land in B3.
- **WGSL / MSL / CUDA emitters are still scalar-only.** They lower every temp to `f32`/`float`; the type-aware vec/mat
  emitter has not been mirrored to them. `KOp::Cast` was added there in B0-3.

## D-008 C0 — the gpu-context program seam ✅ (2026-07-10)

The user rejected the `crd::shader::compile_glsl` gate and directed: **gpu-context handles all the shaders; crd-shader
must not know GLSL or HLSL.** Recorded as ADR-0103 (supersedes ADR-0099 §6, struck in place) and executed as detour
D-008. C0 landed:

- **The two SPIR-V compilers moved `crd-shader` → `gpu-context-vulkan`** verbatim: `compile_glsl_to_spirv` (shaderc) +
